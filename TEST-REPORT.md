POST отправлен как multipart с параметрами из ТЗ. Ответ HTTP 200 получен без cookies и анонимной PHP-сессии. Запрос Python/httpx из работающего FastAPI также получил HTTP 200.

| Дней после заполнения пустых дат | 210 |

Backend не выводит охват семестра из первого и последнего занятия: использует явный `interval`. Даты семестра подтверждены ответом API; окончательную полноту будущих занятий определяет университет.

Backend: сохранение нескольких flows в одной паре, исходных ID и отдельных последовательных пар; нейтральные отсутствующие поля; все восемь интервалов звонков; пустые дни и полностью пустой период; отклонение неизвестного периода и неверной пары; кеш и истечение TTL; 20 параллельных клиентов с одним upstream-запросом; устаревший fallback с неизменным временем получения; предельный возраст fallback; ограничение успешных и неуспешных обновлений; HTTP 404, 429, 503; отсутствие внутренней ошибки в ответе; multipart и отсутствие cookies.

Frontend: неделя ПН–ВС на границе 2026/2027, переход к следующей неделе; 42 ячейки месяца; восемь месяцев семестра; Москва на границе суток UTC; текущая пара и точное исключение времени её окончания; свайпы через границы годов и отсечение коротких жестов; обратный отсчёт следующей пары.

Тестовые ответы используются только в `backend/tests`. Рабочее приложение их не импортирует.

## Проверка сетевой ошибки и исправления

Для отдельного локального запуска таймаут университета временно уменьшен до 0,001 с через переменную окружения процесса. Backend получил ConnectTimeout и вернул HTTP 503; интерфейс показал сообщение и кнопку повторной попытки. Повторное нажатие не вызвало цикл обращений к университету.

Проверка выявила оставшиеся подписи о загрузке после ошибки и нулевые счётчики неизвестных дней в мини-календаре. Исправлено: подписи показывают недоступность, неизвестные даты больше не объявляются свободными. Повторная проверка подтвердила исправление. Затем тестовый процесс остановлен; нормальный запуск с таймаутом 20 с снова получил HTTP 200 и реальное расписание.

Устаревший fallback и предельный возраст проверены автоматическими тестами с управляемым временем; длительное семидневное ожидание в браузере не проводилось. Подсветка текущей пары проверена тестом времени; в момент браузерной проверки занятия ещё не начались, поэтому фиктивная текущая пара не отображалась.

## Ограничения

Поддерживается один реальный поток и период, предоставленный университетом. Кеш находится в памяти одного процесса; после перезапуска требуется новое получение данных. Другие семестры не выдумываются. Внешняя доступность и последующие изменения расписания зависят от РГГУ. Публикация, БД и аккаунты не входят в этот этап.

## Исправление запуска в Windows PowerShell 5.1

После сообщения пользователя о ParserError исправлена кодировка `start.ps1`: UTF-8 без BOM заменена на UTF-8 с BOM (префикс EF-BB-BF). Проверка страницы использует `Invoke-WebRequest -UseBasicParsing`, совместимый с Windows PowerShell 5.1. Добавлен поиск локального Node.js runtime Codex, если `node` отсутствует в PATH.

Повторная проверка выполнена через `powershell.exe -NoProfile -File .\start.ps1 -NoBrowser -SmokeTest`: реальные серверы запущены, страница и health-check доступны, русские сообщения отображаются корректно, процессы остановлены, код завершения 0. Первоначальная проверка скрипта проводилась в PowerShell 7 и не выявляла проблему чтения UTF-8 в версии 5.1.

## Запуск для телефона по локальной сети

Добавлен явный режим `start.ps1 -Lan`. Frontend привязывается к частному адресу физического Wi-Fi/Ethernet адаптера, с приоритетом Wi-Fi. Виртуальные, туннельные и loopback адаптеры не выбираются. Backend остаётся на 127.0.0.1. Правила брандмауэра и маршрутизатора не изменяются.

Проверено в Windows PowerShell 5.1: `start.ps1 -Lan -NoBrowser -SmokeTest` выбрал Wi-Fi и адрес `http://192.168.1.36:5173/`, получил успешные ответы страницы и `/api/health` через Vite proxy, остановил оба процесса и завершился с кодом 0. Обычный режим без `-Lan` также повторно проверен успешно. Кодировка UTF-8 с BOM сохранена. Проверка с физического телефона не проводилась; доступность с него также зависит от общей Wi-Fi сети, её изоляции клиентов и правил Windows Firewall.
