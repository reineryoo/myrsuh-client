# Техническое задание: RGGU Schedule — современное расписание студента РГГУ

## 1. Роль и общая задача

Ты — опытный senior fullstack-разработчик и UI/UX-дизайнер.

Твоя задача — с нуля разработать полноценное, функциональное и визуально качественное веб-приложение для просмотра расписания Российского государственного гуманитарного университета (РГГУ).

Существующий университетский сайт неудобен: студенту приходится постоянно выбирать курс, форму обучения, поток и период расписания.

Наша задача — создать современную альтернативу, которая автоматически загружает расписание, сохраняет выбранную группу и позволяет удобно просматривать занятия.

**Название проекта:** RGGU Schedule.

**Главный приоритет:** современный, красивый и максимально удобный интерфейс. Приложение должно ощущаться как качественный коммерческий продукт, а не как учебный проект.

Разработку вести по принципу desktop-first: сначала полноценный интерфейс для ПК, затем адаптивная версия для планшетов и смартфонов. Тип устройства должен определяться автоматически с помощью адаптивной вёрстки, без отдельного переключателя.

Не ограничивайся созданием макета. Реализуй работающие frontend и backend, подключение к реальному расписанию и всю описанную бизнес-логику.

## 3. Интеграция с реальным API университета

У приложения нет доступа к исходному backend-коду университета, но есть публично используемый HTTP endpoint расписания.

### Endpoint

`POST https://raspis.rggu.ru/api/Get_Schedule_Table`

### Content-Type

`multipart/form-data`

Это принципиально важно: запрос должен отправляться именно как multipart/form-data, а не как JSON.

### Параметры запроса

Использовать следующие реальные значения:

| Поле | Значение |
|---|---|
| eduform | 3 |
| course | 2 |
| intervalMode | 4 |
| menuMode | flow |
| flow | 119_1 |

Пояснения:

- `eduform=3` — очный бакалавриат.
- `course=2` — второй курс.
- `intervalMode=2` — неделя.
- `intervalMode=3` — месяц.
- `intervalMode=4` — семестр.
- `menuMode=flow` — получение по потоку.
- `flow=119_1` — идентификатор моего потока.

**При первоначальной загрузке запрашивать сразу весь семестр через `intervalMode=4`.**

Проверить, что университетский endpoint действительно возвращает полный семестр. Если запрос не работает без предварительной сессии, аккуратно исследовать необходимость анонимной PHP-сессии. Не обходить ограничения доступа.

Не копировать из браузера чужие cookies, токены, PHPSESSID и другие сессионные значения.

Не задавать вручную `Content-Length` и `multipart boundary`. HTTP-клиент должен формировать их самостоятельно.

### Пример запроса через Python

```python
import httpx

UNIVERSITY_URL = (
    "https://raspis.rggu.ru/api/Get_Schedule_Table"
)

payload = {
    "eduform": "3",
    "course": "2",
    "intervalMode": "4",
    "menuMode": "flow",
    "flow": "119_1",
}

async with httpx.AsyncClient(timeout=20) as client:
    response = await client.post(
        UNIVERSITY_URL,
        files={
            key: (None, value)
            for key, value in payload.items()
        }
    )
    response.raise_for_status()
    schedule = response.json()
```

Это пример реализации, а не подтверждение работоспособности запроса. Необходимо проверить реальное поведение endpoint.

### Формат ответа

Университет возвращает JSON приблизительно следующей структуры:

```json
{
  "itemName": "Поток",
  "item": "ИИНиТБ-ФИСБ-ПИ-ПИИ (Группа 1), курс 2, форма обучения: 1-Б-О",
  "interval": "с 02.11.2026 по 08.11.2026",
  "tblData": [
    {
      "date": "02.11.2026 ПН",
      "day": 0,
      "short_date": "02.11",
      "pairs": [
        {
          "pair": 5,
          "flows": [
            {
              "group": "-",
              "subgroup": "-",
              "room": "114(кир)",
              "id_room": "45",
              "subject": "Теория информации",
              "id_subject": "488",
              "lessontype": "лек; сем",
              "id_lessontype": "4",
              "teacher": "Колыбанов К.Ю.",
              "teacher_fullfio": "Колыбанов Кирилл Юрьевич",
              "id_teacher": "860"
            }
          ]
        }
      ]
    }
  ],
  "edYear": "2026/2027",
  "semester": "1 семестр",
  "updatetime": "01.11.2026 22:00"
}
```

Реальный JSON может содержать больше дней, пар и вложенных элементов.

### Важные требования к обработке данных

1. `tblData` содержит дни с занятиями.
2. `pairs` — массив учебных пар внутри дня.
3. `pair` — номер пары, НЕ время её начала.
4. `flows` — массив записей, относящихся к конкретной паре.
5. У одной пары потенциально может быть несколько элементов `flows`. Нельзя терять эти данные.
6. `lessontype` содержит тип занятия.
7. `room` содержит аудиторию.
8. `teacher` и `teacher_fullfio` содержат информацию о преподавателе.
9. `updatetime` — время последнего обновления на стороне университета.
10. Отсутствующие в `tblData` даты необходимо корректно отображать в календаре как дни без занятий, если они входят в запрошенный период.

Не нужно выводить JSON напрямую в интерфейс.

На backend нужно преобразовать ответ университета в нормализованный, типизированный формат, удобный для frontend.

Сохранять номера пар, названия дисциплин, аудитории, преподавателей и исходные идентификаторы.

Не объединять автоматически две последовательные пары одного предмета: каждая пара имеет отдельный номер и время. Визуально их можно группировать, но данные должны сохраняться.

Если в API отсутствуют преподаватель, аудитория или другие сведения, отображать корректные нейтральные значения. Не показывать пользователю `null`, `undefined` и технические заглушки.

## 8. Режимы календаря

Реализовать три режима отображения.

### 8.1. Неделя — основной режим

Это главный экран приложения.

Показывать неделю с понедельника по воскресенье.

В верхней панели:

- Диапазон дат.
- Кнопки предыдущей и следующей недели.
- Кнопка «Сегодня».

Для ПК реализовать удобный недельный календарь, в котором одновременно видны дни недели.

Возможен вариант с колонками дней и карточками занятий внутри них.

Текущий день визуально выделять.

Дни без занятий отображать аккуратно, без загромождения.

Если на конкретный день приходится большое количество занятий, не ломать сетку.

### 8.2. Месяц

Реализовать полноценную сетку календаря на месяц.

Дни должны отображаться привычным календарным форматом.

Для каждого дня показывать количество занятий или компактные индикаторы.

По нажатию на день открывать его расписание.

Добавить переключение месяцев.

Выделять сегодняшний день.

### 8.3. Семестр

Реализовать удобный обзор всего семестра.

Не нужно пытаться одновременно отрисовать огромную таблицу со всеми занятиями.

Лучше реализовать один из подходов:

- компактный календарь по месяцам;
- список недель;
- обзор семестра с возможностью переходить к конкретной дате.

Выбрать наиболее удобное и визуально качественное решение.

При выборе дня или недели пользователь должен быстро переходить к соответствующему расписанию.

### Общая логика

При запуске backend загружает расписание на семестр.

Frontend отображает нужную часть уже полученных данных.

Переключение недель и месяцев внутри загруженного семестра должно происходить мгновенно, без повторных HTTP-запросов к университету.

Если пользователь переходит за пределы периода, доступного в загруженных данных, приложение не должно выдумывать расписание.

Показывать понятное сообщение о недоступном периоде. Если удастся установить корректный способ получения других периодов через университетский API, предусмотреть расширение.

## 9. Логика «Сегодня» и текущих занятий

Приложение должно быть полезным не только как календарь, но и как ежедневный инструмент студента.

Для сегодняшнего дня можно показывать компактную информационную панель:

- Сколько сегодня пар.
- Во сколько первая пара.
- Во сколько последняя пара заканчивается.
- Какая пара идёт сейчас.
- Какая пара следующая.

Если сейчас проходит занятие, соответствующую карточку нужно аккуратно выделять.

Можно отображать небольшой прогресс-бар, показывающий, сколько времени занятия уже прошло.

Если занятий сегодня нет — показывать приятное сообщение «Сегодня пар нет».

Если текущие занятия закончились — «На сегодня всё».

Время должно определяться корректно, с учётом часового пояса университета.

Не отображать фиктивные текущие пары.

## 10. Backend API

Разработать собственный REST API на FastAPI.

Минимально необходимые endpoints:

### GET /api/groups

Возвращает список доступных групп.

Пока содержит одну группу, но должен быть расширяемым.

### GET /api/schedule

Возвращает нормализованное расписание выбранного потока.

Пример:

`GET /api/schedule?group_id=119_1`

На первом этапе разрешать только заранее зарегистрированные ID групп.

Нельзя позволять клиенту передавать произвольный URL для запроса через backend.

### POST /api/schedule/refresh

Принудительное обновление кеша расписания.

Предусмотреть защиту от частых повторных запросов.

Не делать этот endpoint способом бесконтрольной отправки запросов на сервер университета.

### GET /api/health

Простой health-check.

### Кеширование

При первом запросе на выбранную группу:

1. Проверить кеш.
2. Если данных нет — отправить запрос к университету.
3. Провалидировать ответ.
4. Нормализовать его.
5. Сохранить в кеше.
6. Вернуть клиенту.

TTL кеша — 15 минут.

Если кеш устарел, попытаться обновить данные.

Если сервер университета временно недоступен, но ранее были получены корректные данные, по возможности вернуть предыдущую версию расписания с признаком устаревших данных.

Не хранить кеш бесконечно без контроля времени обновления.

Реализовать защиту от одновременной отправки множества одинаковых запросов при параллельном открытии сайта несколькими пользователями.

Добавить разумные таймауты, обработку HTTP-ошибок и логирование.

Не возвращать пользователю внутренние traceback или чувствительную техническую информацию.

## 11. Состояния интерфейса

Обязательно реализовать все основные состояния.

Если в периоде вообще отсутствуют занятия, показать отдельное дружелюбное сообщение.

### Error state

Если университетский API недоступен:

«Не удалось загрузить расписание. Попробуйте ещё раз».

Добавить кнопку повторной попытки.

### Stale data

Если используются ранее сохранённые данные, показывать ненавязчивое предупреждение.

### Refresh

Добавить кнопку обновления расписания.

Во время запроса показывать индикатор выполнения.

Не блокировать весь интерфейс, если уже есть доступные данные.

### Last update

Отображать два разных значения, если они доступны:

- Когда данные обновлены университетом (`updatetime`).
- Когда наше приложение последний раз успешно получило данные.

Не путать эти временные метки.

## 15. Дополнительные требования

### Производительность

- Не отправлять запрос к университету при каждом переключении дня.
- Не обновлять расписание при каждом рендере React.
- Избегать лишних сетевых запросов.
- Использовать кеширование.
- Интерфейс должен отзывчиво реагировать на действия пользователя.

- Не хранить чувствительные данные в frontend.
- Не копировать реальные пользовательские сессии.
- Не использовать обходы авторизации или защиты университетского сайта.
- Ограничить параметры запросов к backend.
- Учитывать правила использования университетского API.
- Не перегружать сервер университета.

### Качество кода

- TypeScript без необоснованного `any`.
- Pydantic-модели для данных.
- Понятная обработка ошибок.
- Читаемые названия функций и компонентов.
- Переиспользуемые UI-компоненты.
- Отсутствие дублирования бизнес-логики.

### Тестирование

Предусмотреть проверки:

1. Корректности нормализации JSON.
2. Корректности определения времени каждой пары.
3. Обработки пустых дней.
4. Отображения нескольких `flows` в одной паре.
5. Корректности переключения недель на границе месяцев и годов.
6. Сохранения группы после перезагрузки.
7. Обработки недоступного университетского API.
8. Корректной работы кеша.

Для тестов использовать mock-ответы, но не подменять ими реальные данные в production.
